# Конспект для захисту: як працює HR-асистент

Цей файл для власника проєкту: щоб упевнено пояснити систему на відео і відповісти на питання викладачів. Він написаний українською, решта документації англійською.

## 1. Що це за система (30 секунд)

HR-асистент для вигаданої IT-компанії **Lumora Tech**. Працівник пише в чат, і асистент робить одне з чотирьох:
1. **Відповідає** на питання про HR-політики, лише з тексту політик і **з посиланням на розділ** (`[leave-policy §3.4]`).
2. **Ставить уточнювальне питання**, якщо відповідь залежить від фактів, яких він не знає (наприклад, «скільки днів ви хворієте?»).
3. **Працює з відпустками:** подати, перевірити залишок, скасувати; HR може затвердити або відхилити. Дані лежать у базі SQLite, до якої **доступ є лише через tool calls, які вирішує зробити LLM**.
4. **Передає питання до HR** (створює тікет), якщо політики не дають відповіді. Асистент не вигадує.

**Чому це не «vanilla RAG»:** є маршрутизація між джерелами (документи, база, людина), збір інформації перед пошуком, гібридний пошук з reranking, відмова відповідати з передачею до HR і агент з інструментами над базою.

## 2. Шлях одного повідомлення (walkthrough)

Приклад: *«Do I need a sick note?»* від Andrii Koval (full-time, Львів).

1. **Guard** (`components/guard.py`, правила без LLM) перевіряє, чи це не prompt injection, і маскує персональні дані (картка, IBAN, телефон).
2. **Router** (`components/router.py`, **LLM-виклик**) класифікує повідомлення в один із 5 класів: `policy_question` / `leave_action` / `hr_referral` / `smalltalk` / `unclear`. Тут це `policy_question`.
3. **Collector** (`components/collector.py`, **LLM-виклик** + код) визначає, від яких фактів залежить відповідь. Профільні факти (тип зайнятості, офіс, випробувальний термін) береться з «довідника працівників», тобто з логіну. Тут потрібна тривалість хвороби, а її ніхто не назвав, тому асистент питає: *«How many working days have you been ill?»*.
4. Користувач відповідає «4 days». Pipeline пам'ятає початкове питання, collector бачить відповідь (а якщо LLM її не витягне, спрацює запасний regex у коді).
5. **Rewriter** (**LLM-виклик**) робить пошуковий запит, зрозумілий без контексту розмови: *«sick leave 4 days medical certificate required»*.
6. **Hybrid retrieval** (локально, без API):
   - **BM25** шукає за ключовими словами;
   - **dense-ембединги** (`bge-small`) шукають за змістом;
   - **RRF** (Reciprocal Rank Fusion) зливає два рейтинги в один;
   - на виході топ-20 розділів.
7. **Reranker** (локальний cross-encoder) уважно переоцінює пари «запит + розділ» і залишає топ-5.
8. **Answerer** (**LLM-виклик**) відповідає лише з цих 5 розділів, повертає JSON `{answer, citations, sufficient}` і застосовує правило до конкретної людини. Тут відповідь: «більше 3 днів потребує довідки [sick-leave-policy §2.3]».
9. Якщо `sufficient=false`, спрацьовує **Referral**: LLM формулює суть і викликає tool `create_hr_ticket`, у базі з'являється тікет.
10. **Tracer** (`llm.py`) записує кожен LLM-виклик і tool call (промпт, версія, токени, ціна, час) у трейс. Його видно в UI («Show trace»).

**Гілка відпусток:** *«Book annual leave 7–11 December»* → router дає `leave_action` → **leave agent** (ReAct-цикл: LLM вирішує → викликає tool → бачить результат → відповідає). Tool `submit_leave_request` викликає **rule engine** (`rules.py`, чистий код), а той рахує робочі дні, залишок, строк попередження і перетини з командою. Рішення: approved, declined або pending_hr.

## 3. Ключові рішення і чому саме так

| Рішення | Чому |
|---|---|
| Рішення про відпустку приймає код, а не LLM | Бізнес-правила детерміновані, їх треба тестувати на 100%. LLM лише збирає дані й пояснює рішення |
| База доступна тільки через tools | Вимога умови «access it via LLM only». UI базу взагалі не читає |
| Профіль із «довідника», а не з бази | Профіль — це те, хто залогінений (як SSO). Відпустки — це дані, і до них доступ лише через LLM |
| Гібридний пошук + reranker | Ablation показав, що кожен крок покращує MRR (див. звіт) |
| Чанк = один розділ політики | Цитата — це розділ. Ablation: нарізка по розділах значно краща за фіксовані вікна по 120 слів |
| Рядки таблиць індексуються окремо | Значення з таблиці (500 грн для part-time) інакше губилося, бо reranker відсіював велику таблицю (ітерація 2) |
| Суддя — інша модель (Gemini), ніж генератор (GPT-4o-mini) | Модель схильна завищувати оцінки «своїм» відповідям. Суддю відкалібровано на контрольних прикладах |
| HR-рішення лише з підтвердженням | Незворотна дія, тому потрібен human-in-the-loop (лекція про агентів) |

## 4. Evals, які варто пам'ятати

- **Метрики з умови** (кожна має свою цифру у звіті):
  - збір інформації: F1 фактів і precision/recall уточнювальних питань;
  - успішність retrieval: Hit@5, MRR;
  - коректність відповіді: суддя;
  - підтримка джерелом: faithfulness і citation hit;
  - перенаправлення до HR: precision/recall.
- **dev / test / holdout:**
  - промпти покращувалися на dev;
  - test показав перенавчання на dev (оцінки впали);
  - після аналізу помилок зроблено ітерацію 2;
  - holdout (написаний ДО виправлень) дає чесну оцінку.
- **«Перший етап, де губиться відповідь»:** oracle-варіант (answerer з правильними розділами) показав, що головна проблема ітерації 1 була в надмірній обережності answerer, а не в пошуку.
- **Guard на правилах** має розрив dev/test: leetspeak і рольові ігри проходять. Відповідь на це: захист у глибину (tools перевіряють права, HR-рішення потребують підтвердження).

## 6. Можливі питання викладачів

- **Чому gpt-4o-mini?** Дешева (вся розробка разом з усіма evals коштувала ≈ $0.32), надійно викликає tools, підтримує structured outputs.
- **Як ви знаєте, що суддя правий?** Калібрування на 19 контрольних прикладах з відомою відповіддю: рішення «пройшло / не пройшло» правильне на 100%, точний рівень збігається в 95% випадків.
- **Чому оцінки на test нижчі, ніж на dev?** Промпти тюнились на dev. Тому є holdout, і порівняння показано в таблиці «Iteration comparison».
- **Що б ви покращили далі?**
  - guard на основі класифікатора замість регулярних виразів;
  - більший holdout;
  - перевірка відповіді на суперечності з профілем;
  - реальна автентифікація.
